# Анализ границ ответственности

**Система:** Мини-CRM «Фриланс без паники»  
**Сценарий:** Создание сделки и выставление инвойса

---

## 1. Транзакционные границы

### 1.1. Где начинается и заканчивается транзакция?

**Начало транзакции (первой):** Менеджер нажимает кнопку "Сохранить и перейти к инвойсу"

**Конец транзакции (успешный сценарий):**
- **Основная транзакция БД №1:** Сделка сохранена со статусом "NEGOTIATION"
- **Основная транзакция БД №2:** Инвойс создан + Сделка обновлена до статуса "INVOICED" + Платёжная ссылка сохранена
- **Побочные эффекты (асинхронные):** Email с инвойсом отправлен клиенту

**Важно:** У нас две отдельные транзакции:
1. **Создание сделки** - атомарно
2. **Выставление инвойса + генерация платёжной ссылки** - атомарно (но может откатиться независимо от п.1)

Если выставление инвойса не удалось, сделка остаётся в статусе `NEGOTIATION`, и инвойс можно выставить позже.

### 1.2. Какие операции должны быть атомарными?

#### Транзакция №1: Создание сделки

**Атомарные операции (в одной БД-транзакции):**
1. Валидация входных данных (клиент, название, бюджет, услуга)
2. Создание записи Deal в таблице `deals` со статусом "NEGOTIATION"
3. Проверка бюджета на превышение лимита (если лимит превышен - перевести в статус "APPROVAL")

**Обоснование:** Сделка без клиента или без названия не имеет смысла. Если создание сделки не удалось - всё должно откатиться.

**Пример сбоя:**
- Если создание сделки удалось, но проверка бюджета показала ошибку → ROLLBACK всей транзакции
- Иначе получим "сделку-призрак" без статуса или с невалидными данными

#### Транзакция №2: Выставление инвойса

**Атомарные операции (в одной БД-транзакции):**
1. Проверка существования сделки и её статуса (не должна быть уже "INVOICED")
2. Создание записи Invoice в таблице `invoices` со статусом "PENDING"
3. Обновление статуса сделки на "INVOICED"
4. Генерация платёжной ссылки через платёжный шлюз (синхронно)
5. Сохранение платёжной ссылки в записи инвойса

**Обоснование:** Инвойс должен быть неразрывно связан со сделкой. Если платёжная ссылка не сгенерировалась - инвойс бесполезен.

### 1.3. Какие операции могут быть асинхронными?

| Операция | Обоснование |
|----------|-------------|
| Отправка email с инвойсом клиенту | Может быть отложена. Инвойс уже создан, email - это "best-effort" действие |
| Запись событий в журнал событий (Events Log) | Eventual consistency допустима. События можно записать асинхронно через event sourcing |
| Обновление статистики менеджера (количество сделок) | Можно пересчитать позже |
| Синхронизация с CRM (если есть) | Не влияет на бизнес-логику |
| Отправка уведомления менеджеру об успешной оплате | Это уже после основной транзакции |

**Принцип:** Если операция НЕ нарушает инварианты доменной модели при отказе - она может быть асинхронной.

## 2. Таблица транзакционных границ

| Операция | Синхронная/Асинхронная | Откат при ошибке | Retry-стратегия | Идемпотентность |
|----------|------------------------|------------------|-----------------|-----------------|
| **Валидация входных данных (клиент, сумма)** | Синхронная | Нет (просто возврат ошибки) | N/A | Да (чтение без side-effects) |
| **Создание записи Deal в БД** | Синхронная | Да (ROLLBACK транзакции №1) | Нет (контролируется БД) | Да (проверка дублей по `idempotency_key`) |
| **Проверка бюджета на превышение лимита** | Синхронная | Да (ROLLBACK транзакции №1) | Нет | Да |
| **Генерация уникального deal_id** | Синхронная | Нет (детерминированная генерация) | N/A | Да (UUID v4 или формат D-YYYY-NNNN) |
| **Проверка существования сделки и её статуса** | Синхронная | Да (откат транзакции №2 при невалидном статусе) | Нет | Да |
| **Создание записи Invoice в БД** | Синхронная | Да (ROLLBACK транзакции №2) | Нет | Да (проверка дублей по deal_id) |
| **Обновление статуса Deal на INVOICED** | Синхронная | Да (в той же транзакции №2) | Нет | Да |
| **Генерация платёжной ссылки через Payment Gateway** | Синхронная | Да (ROLLBACK транзакции №2) | 3 попытки с экспоненциальной задержкой (1s, 2s, 4s) | Да (по invoice_id) |
| **Сохранение платёжной ссылки в инвойсе** | Синхронная | Да (в той же транзакции №2) | Нет | Да |
| **Публикация доменных событий (DealCreated, InvoiceCreated)** | Синхронная (в transactional outbox) | Да (в той же транзакции) | Нет (часть основной транзакции) | Да (проверка дублей по event_id) |
| **Отправка email с инвойсом клиенту** | Асинхронная (через очередь) | Нет (инвойс уже создан) | 5 попыток с exponential backoff (1min, 5min, 15min, 1h, 6h) | Да (дедупликация по invoice_id + email) |
| **Запись событий в журнал событий (Events Log)** | Асинхронная (event sourcing) | Нет (best-effort) | 3 попытки | Да (дедупликация по event_id) |
| **Обновление кэша статистики менеджера (Redis)** | Асинхронная | Нет (eventual consistency) | 3 попытки с задержкой 1s | Да |

## 3. Обработка отказов внешних сервисов

### 3.1. Платёжный шлюз недоступен (Payment Gateway)

**Проблема:** Сервис генерации платёжных ссылок не отвечает (таймаут, 503 Service Unavailable)

**Стратегия:**
1. **Таймаут:** 5 секунд (для синхронного вызова)
2. **Основная транзакция:** НЕ откатывается полностью, но инвойс создаётся в статусе "PENDING_RETRY"
3. **Retry:**
   - Помещаем задачу в очередь `retry_queue` с типом "PAYMENT_LINK_GENERATION"
   - Фоновый worker пытается сгенерировать ссылку повторно
   - Retry schedule: через 30 секунд, затем 1 минута, 2 минуты, 5 минут, 15 минут
   - После 5 неудачных попыток → помечаем инвойс как "FAILED" и алертим админа
   - Отправляем уведомление менеджеру: "Не удалось сгенерировать платёжную ссылку. Требуется ручное вмешательство."
4. **Компенсация:** Нет (инвойс уже создан, сделка в статусе "INVOICED" - это нормально)
5. **Уведомление пользователя:** "Сделка создана, инвойс выставлен. Платёжная ссылка будет сгенерирована автоматически позже."

**Обоснование:** Платёжный шлюз - критичный компонент для приёма оплаты, но временные сбои не должны блокировать создание сделки. Retry-механизм позволяет восстановиться без потери данных.

### 3.2. Email-сервис недоступен

**Проблема:** Сервис отправки email не отвечает (таймаут, 503 Service Unavailable)

**Стратегия:**
1. **Таймаут:** 10 секунд
2. **Основная транзакция:** НЕ откатывается (инвойс уже создан, платёжная ссылка сгенерирована)
3. **Retry:**
   - Помещаем email в очередь `notification_queue`
   - Фоновый worker пытается отправить повторно
   - Retry schedule: через 1 минуту, затем 5 минут, 15 минут, 1 час, 6 часов
   - После 5 неудачных попыток → помечаем как "failed" и алертим админа
   - Отправляем fallback-уведомление менеджеру: "Email клиенту не отправлен. Скопируйте платёжную ссылку вручную."
4. **Компенсация:** Нет (инвойс уже выставлен, это нормально)
5. **Уведомление пользователя:** "Инвойс создан! Не удалось отправить email клиенту. Вы можете скопировать платёжную ссылку и отправить её вручную."

**Обоснование:** Email - это приятный бонус, но не критично. Менеджер может отправить ссылку вручную через мессенджер или телефон.

### 3.3. База данных недоступна

**Проблема:** PostgreSQL не отвечает (connection refused, timeout)

**Стратегия:**
1. **Таймаут:** 5 секунд для connection, 30 секунд для query
2. **Основная транзакция:** ROLLBACK (сделка и инвойс НЕ создаются)
3. **Retry:**
   - На уровне приложения: 3 попытки с экспоненциальной задержкой (1s, 2s, 4s)
   - Если все 3 попытки не удались → возвращаем 503 Service Unavailable
4. **Компенсация:** Нет (ничего не было создано)
5. **Offline-режим:**
   - Если менеджер работает с плохим интернетом → сохраняем сделку локально (IndexedDB/LocalStorage)
   - При восстановлении связи → синхронизируем с сервером
6. **Уведомление пользователя:** "Не удалось создать сделку. Попробуйте ещё раз или свяжитесь с техподдержкой."

**Обоснование:** БД - это критичный компонент. Без неё сделка не может существовать. Для временных сбоев нужен retry.

### 3.4. Конкурентное выставление инвойса по одной сделке

**Проблема:** Два менеджера одновременно пытаются выставить инвойс по одной сделке

**Стратегия:**
1. **Блокировка:** Используем `SELECT ... FOR UPDATE` при проверке статуса сделки
   ```sql
   SELECT * FROM deals 
   WHERE id = 'D-2026-001' AND status != 'INVOICED'
   FOR UPDATE;
2. **Основная транзакция №2:** ROLLBACK (инвойс НЕ создаётся для второго менеджера)
3. **Retry:** Автоматически обновляем страницу и показываем уже существующий инвойс
4. **Компенсация:** Сделка остаётся в статусе "INVOICED" (первый менеджер успешно создал инвойс)
5. **Уведомление пользователя:** "Инвойс по данной сделке уже был выставлен. Обновите страницу.

**Обоснование:** Pessimistic locking предотвращает race condition. Это критично для избежания дублирования инвойсов.

## 4. Идемпотентность

### 4.1. Проблема: Повторное нажатие кнопки "Выставить инвойс"

**Сценарий:** Менеджер дважды кликнул на кнопку из-за медленного интернета

**Решение:**
1. **Frontend:** Блокировать кнопку после первого клика (disable button)
2. **Backend:** Проверять `idempotency_key` в запросе
   ```json
   {
    "deal_id": "D-2026-001",
    "idempotency_key": "manager-789_2026-03-12_14-30-15"
   }
   ```
3. **Логика:**
   - При получении запроса проверяем таблицу `idempotent_requests`
   - Если `idempotency_key` уже есть → возвращаем кэшированный ответ (invoice_id, payment_url)
   - Если нет → обрабатываем запрос и сохраняем в `idempotent_requests`
4. **TTL ключей:** 24 часа (после этого можно повторить создание с тем же ключом)

**Пример таблицы:**
```sql
CREATE TABLE idempotent_requests (
  idempotency_key VARCHAR(128) PRIMARY KEY,
  endpoint VARCHAR(255) NOT NULL,
  response_body JSONB NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_idempotent_created ON idempotent_requests(created_at);
-- Очистка старых записей по cron (старше 24 часов)
```

### 4.2. Проблема: Дубликаты email-уведомлений

**Сценарий:** Notification Service получил запрос дважды из-за retry

**Решение:**
1. В таблице `notification_queue` добавляем уникальный ключ:
   ```sql
   CREATE UNIQUE INDEX idx_notification_dedup 
   ON notification_queue(request_id, group_id, recipient_phone, notification_type);
   ```
2. При попытке добавить дубликат → игнорируем (ON CONFLICT DO NOTHING)
3. SMS-провайдер также должен поддерживать дедупликацию через `Message-ID`

### 4.3. Проблема: Повторное создание сделки с теми же данными

**Сценарий:** Менеджер дважды нажал "Сохранить" из-за задержки ответа сервера

**Решение:**
1. Проверяем, есть ли уже сделка с таким же client_id, title и датой создания (в пределах 5 минут):
   ```sql
    SELECT * FROM deals 
    WHERE client_id = 123 
    AND title = 'Разработка лендинга'
    AND created_at > NOW() - INTERVAL '5 minutes'
    AND status != 'CANCELLED';
   ```
2. Если сделка уже существует → возвращаем её ID (не создаём новую)
3. Если статус сделки NEGOTIATION или INVOICED → запрещаем создание новой
4. Уведомление: "Сделка с такими данными уже существует. ID: D-2026-001"

### 4.4. Проблема: Генерация платёжной ссылки дважды

**Сценарий:** Фоновый worker дважды обработал одну и ту же задачу из очереди

**Решение:**
1. Используем idempotency_key в запросе к платёжному шлюзу:
   ```sql
    {
    "amount": 1500.00,
    "currency": "USD",
    "invoice_id": "INV-2026-001",
    "idempotency_key": "INV-2026-001_1234567890"
    }
   ```
2. Платёжный шлюз возвращает ту же ссылку при повторном запросе с тем же ключом
3. В БД проверяем, есть ли уже payment_url для этого инвойса → если есть, не обновляем

## 6. Метрики и мониторинг

**Ключевые метрики для отслеживания:**

| Метрика | Цель | Алерт при |
|---------|------|-----------|
| `deal_creation_latency_p95` | < 2 секунды | > 4 секунд |
| `deal_creation_success_rate` | > 99% | < 98% |
| `invoice_creation_latency_p95` | < 4 секунды | > 8 секунд |
| `invoice_creation_success_rate` | > 99% | < 98% |
| `db_connection_pool_active` | < 80% от макс. | > 90% |
| `notification_queue_size` | < 500 | > 2000 |
| `email_delivery_rate` | > 98% в течение 5 минут | < 95% |
| `payment_gateway_timeout_count` | 0 | > 5/hour |
| `payment_gateway_retry_count` | < 10/hour | > 50/hour |
| `concurrent_invoice_conflicts` | < 5/hour | > 20/hour |
| `offline_sync_pending_count` | 0 | > 50 |
| `idempotency_key_usage_rate` | < 5% запросов | > 10% запросов |

**Логирование:**
- **INFO:** Успешное создание сделки и инвойса
- **INFO:** Генерация платёжной ссылки (с payment_id)
- **WARNING:** Email Service timeout, поместили в очередь
- **WARNING:** Платёжный шлюз timeout, инвойс в статусе PENDING_RETRY
- **WARNING:** Конкурентное выставление инвойса, откатили транзакцию
- **ERROR:** БД недоступна, откатили транзакцию
- **ERROR:** Платёжный шлюз вернул ошибку после 5 retry
- **CRITICAL:** Очередь уведомлений переполнена (> 5000)
- **CRITICAL:** Более 10% инвойсов не могут сгенерировать платёжную ссылку

## 7. Выводы

### Ключевые решения:

1. ✅ **Две транзакции:** Создание сделки (Tx1) и выставление инвойса (Tx2) - разделены для гибкости, что позволяет выставлять инвойс позже или повторно при сбоях.
2. ✅ **Атомарность:** Сделка создаётся в одной транзакции; Инвойс + обновление сделки + платёжная ссылка - в другой, что гарантирует целостность данных в каждом шаге.
3. ✅ **Асинхронность:** Email-уведомления и запись событий вынесены в очередь, что ускоряет основной сценарий и обеспечивает отказоустойчивость при сбоях внешних сервисов.
4. ✅ **Идемпотентность:** Использование `idempotency_key` для дедупликации запросов предотвращает создание дубликатов сделок и инвойсов при повторных нажатиях или retry.
5. ✅ **Pessimistic Locking:** Применение `SELECT ... FOR UPDATE` для избежания конкурентного выставления инвойсов гарантирует, что по одной сделке будет создан только один активный инвойс.
6. ✅ **Отказоустойчивость:** 
   - Сделка не откатывается при сбое платёжного шлюза (инвойс создаётся в статусе `PENDING_RETRY`)
   - Offline-режим позволяет менеджерам работать при плохом интернете с последующей синхронизацией
7. ✅ **Retry-стратегии:** 
   - Exponential backoff для временных сбоев (1s, 2s, 4s для платёжного шлюза; 1min, 5min, 15min, 1h, 6h для email)
   - После 5 неудачных попыток - алерт администратора и ручное вмешательство
8. ✅ **Мониторинг:** Система метрик для каждого критичного компонента с порогами алертов позволяет оперативно реагировать на проблемы.
9. ✅ **Eventual Consistency:** События записываются асинхронно через event sourcing, что не влияет на основной бизнес-процесс.

### Транзакционные инварианты:

- **Инвариант №1:** Сделка без клиента или без названия недействительна → откатываем Tx1
- **Инвариант №2:** Инвойс не может быть выставлен по уже оплаченной или отменённой сделке → проверяем статус перед созданием
- **Инвариант №3:** К одной сделке может быть привязан только один активный инвойс → unique constraint на `invoices.deal_id` для статусов PENDING, PENDING_RETRY
- **Инвариант №4:** Сумма инвойса должна строго равняться сумме сделки → проверка перед созданием и CHECK constraint в БД
- **Инвариант №5:** Платёжная ссылка должна быть уникальной для каждого инвойса → уникальный индекс на `payment_url`

### Компромиссы:

- **Eventual consistency для email уведомлений:** Клиент может получить инвойс с задержкой до 6 часов (в худшем случае), но это приемлемо, так как менеджер может отправить ссылку вручную через мессенджер или телефон.
- **Синхронная генерация платёжной ссылки:** Увеличивает время создания инвойса на 1-3 секунды, но гарантирует, что платёжная ссылка готова к использованию сразу после создания.
- **Хранение idempotency keys 24 часа:** Занимает дополнительное место в БД (около 1-2 ГБ в месяц при 1000 сделок/день), но предотвращает дубликаты и обеспечивает идемпотентность.
- **Две отдельные транзакции вместо одной:** Увеличивает количество обращений к БД, но даёт гибкость: сделка может существовать без инвойса, что полезно для черновиков и согласований.
- **Pessimistic locking вместо optimistic:** Снижает конкурентность при одновременном выставлении инвойсов (блокировка строки), но гарантирует отсутствие race condition, что критично для финансовых операций.

### Риски и их митигация:

⚠️ **Риск 1:** Очередь email уведомлений может переполниться при массовом создании инвойсов (например, в конце месяца)
- **Митигация:** Установить лимит очереди 5000 сообщений, алерт при превышении 80%, авто-масштабирование воркеров

⚠️ **Риск 2:** Платёжный шлюз может быть недоступен длительное время, накапливая очередь retry
- **Митигация:** После 5 неудачных попыток (общая задержка ~30 минут) переводить инвойс в статус "FAILED", уведомлять администратора и менеджера для ручного вмешательства

⚠️ **Риск 3:** Race condition при одновременном выставлении инвойсов для одной сделки
- **Митигация:** Использовать SELECT FOR UPDATE + уникальный индекс на (deal_id, status) для активных инвойсов (PENDING, PENDING_RETRY)

⚠️ **Риск 4:** Менеджер может создать дублирующуюся сделку (один клиент, один проект)
- **Митигация:** Проверка дубликатов по client_id + title в пределах 5 минут, предложение использовать существующую сделку
  
⚠️ **Риск 5:** Потеря данных при offline-синхронизации
- **Митигация:** Использовать local storage с versioning, конфликт резолвинг по принципу "последняя запись побеждает" с ручным подтверждением менеджера
  
⚠️ **Риск 6:** Утечка платёжных ссылок при логировании
- **Митигация:** Маскировать payment_url в логах (например, "pay.example.com/...****"), использовать шифрование при хранении в БД

### Достигнутые цели:

1. **Надёжность:** Система сохраняет данные даже при сбоях внешних сервисов (payment gateway, email service)
2. **Целостность:** Транзакционные инварианты защищают от некорректных состояний (дубликаты инвойсов, неверные суммы)
3. **Масштабируемость:** Асинхронная обработка уведомлений позволяет обрабатывать пиковые нагрузки (до 70 сделок/день)
4. **Прозрачность:** Метрики и логи позволяют отслеживать состояние системы и быстро реагировать на проблемы
5. **Удобство использования:** Offline-режим и идемпотентность делают работу менеджера комфортной даже при нестабильном интернете
